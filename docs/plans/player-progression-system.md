# План: система прогрессии игрока (статистика → опыт → уровни → скины)

Статус: этапы 1 и 3 реализованы и проверены (2026-08-10, 2026-08-11); этапы 1.5, 2, 4a, 4b и 5 не начаты.
Работа ведётся в текущей ветке — отдельная ветка под задачу не заводится (правило `CLAUDE.md`).

## Зачем

В проекте нет учёта достижений игрока: сыгранные раунды, killfeed и табло живут только до конца
матча. Нужно считать победы/поражения и устранения, начислять за них опыт, копить его **локально
на машине игрока** (прогресс едет за игроком, а не привязан к серверу), выдавать уровни и открывать
по уровням скины оружия. Скины должны видеть **все** игроки, а не только владелец. Первая итерация —
перекрасы существующих моделей, чтобы проверить всю цепочку целиком.

Согласованные с владельцем проекта решения:

| Вопрос | Решение |
|--------|---------|
| Детект ботов | Сервер шлёт клиенту флаг (ReGameDLL знает `FL_FAKECLIENT` точно) |
| Профиль | Отдельный файл на каждый SteamID64, фолбэк — общий локальный |
| Опыт | За килл, хедшот, победу/поражение в раунде и в матче; боты дают 30% |
| Объём скинов | 2 ствола × 2 перекраса (AK-47, AWP — красный и золотой) |
| Формат конфигов | KV-текст как `scripts/HudLayout.txt`, парсинг `COM_ParseFile` |

## Архитектура

Разделение продиктовано тем, кто чем владеет в движке:

| Слой | Отвечает за | Почему |
|------|-------------|--------|
| Клиент (`cl_dll`) | Профиль, XP, уровни, разблокировки, свой viewmodel | Прогресс локальный и должен работать на любом сервере; предсказание владеет своим viewmodel |
| Сервер (ReGameDLL `mp.dll`) | Флаг «бот», подмена p_-модели для всех | Только сервер знает `FL_FAKECLIENT` и рассылает третьеличную модель всем клиентам |

Обмен — два уже существующих в движке канала:
- клиент → сервер: userinfo-ключ `cse_skins` (тот же механизм, что `cse_sid` в TeamBar);
- сервер → клиент: новое user message `CseInfo` с битовой маской слотов-ботов.

### Победа в раунде: почему нельзя просто ловить рост счёта

`TeamScore` — это **не** событие «раунд закончился», а трансляция текущего счёта. Сервер шлёт её:

- `MSG_ONE` полным состоянием при коннекте и каждом спавне (`multiplay_gamerules.cpp:3458`,
  `player.cpp:7654`) — зашёл в матч на 5:3, и наивная дельта начислит 5 побед и 3 поражения
  за раунды, которых игрок не играл;
- `MSG_ALL` из `UpdateTeamScores()` — а её зовут из ~20 мест `multiplay_gamerules.cpp`, не только
  на конце раунда;
- после сброса счёта (`m_iNumCTWins = 0` — `multiplay_gamerules.cpp:382, 1804, 1974`: смена сторон,
  рестарт) — дельта отрицательная.

**Правило:** счётчики раундов на сервере меняются только как `++` или `= 0` (проверены все 13 мест
мутации), поэтому начислять XP **только при `delta == +1`**. Одно условие закрывает и полный синк,
и сброс. Логика в `cse_profile.cpp`:

```
на TeamScore(szTeamName, iScore):
    iTeam = TeamNameToNumber(szTeamName)          // "CT"/"TERRORIST", как в MsgFunc_TeamInfo
    if !m_bSeeded[iTeam]:                          // первое сообщение за карту — только засев
        m_iLastScore[iTeam] = iScore; m_bSeeded[iTeam] = true; return
    delta = iScore - m_iLastScore[iTeam]
    m_iLastScore[iTeam] = iScore                   // счётчик обновляем ВСЕГДА
    if delta != 1: return                          // синк, сброс или шум
    iMine = g_PlayerExtraInfo[m_iPlayerNum].teamnumber
    if iMine != TEAM_CT && iMine != TEAM_TERRORIST: return   // спектатор/UNASSIGNED — не начисляем
    CSE_AwardXP( iTeam == iMine ? XP_ROUND_WIN : XP_ROUND_LOSS )
```

Засев `m_bSeeded[]` нужен из-за краевого случая «зашёл ровно на счёте 0:1»: там дельта была бы
законной `+1`. Флаги и `m_iLastScore[]` сбрасываются на новой карте — по образцу
`CHudBase::InitHUDData()`.

Сопоставление имени команды с номером **уже есть в коде** и делать своё не надо: `MsgFunc_TeamInfo`
(`cl_dll/hud/scoreboard.cpp:591-621`) переводит `"TERRORIST"`/`"CT"` в `TEAM_TERRORIST`/`TEAM_CT`.
`TeamScore` несёт те же самые строки (`multiplay_gamerules.cpp:599,604`), так что достаточно
повторить те же два `strcmp`. Смена сторон в халфтайме отрабатывает сама: `teamnumber` игрока
обновляется через `TeamInfo`/`ScoreInfo`, а счётчики обнуляются и переседятся.

**Итог матча** берётся из собственных `m_iLastScore[TEAM_CT]` / `m_iLastScore[TEAM_TERRORIST]` на
переходе `m_iIntermission` из 0 в 1 (поле пишется каждый кадр в `cl_dll/hud_redraw.cpp:109`, так что
нужен именно фронт, а не факт `!= 0`). Ничья — без XP.

⚠️ **У матчевого XP та же дыра, что закрыта правилом `delta == +1` для раундов**: зашёл на 15:14,
матч тут же кончился — и наивная проверка выдала бы полные `match_win`. Поэтому матч засчитывается
только при **участии**: за эту карту начислён хотя бы один `round_win`/`round_loss` (счётчик
`m_iRoundsThisMap`, сбрасывается там же, где `m_bSeeded[]`). Ноль сыгранных раундов → матчевого XP
нет вообще, ни за победу, ни за поражение.

Попутно — **хирургический фикс off-by-one** в `MsgFunc_TeamScore`: цикл `for(i = 0; i < m_iNumTeams; i++)`,
а страж после него `if(i > m_iNumTeams)` промах не ловит (нужно `>=`). Реальные последствия скромнее,
чем кажется: `MAX_TEAMS = 64`, массив `g_TeamInfo[MAX_TEAMS+1]` (`cl_dll/hud.h:58,562`), а команд в CS
не больше трёх — то есть запись уходит в **пустой** слот `g_TeamInfo[m_iNumTeams]`, не за границу и не
в чужую команду. Вред в том, что в этом слоте остаётся `scores_overriden = TRUE` и мусорный `frags`,
которые всплывут, если слот потом займёт настоящая команда. Фикс всё равно делаем — он однострочный.
Обрати внимание: прогрессия на `g_TeamInfo` **не завязана**, она ведёт свои `m_iLastScore[]`, поэтому
фикс — гигиена табло, а не предусловие этапа.

Поля `unlocked` **нет намеренно**: разблокировки полностью выводятся из `xp` → уровня → порогов в
`CseProgression.txt`. Хранить их отдельно значило бы завести второй источник правды рядом с уже
объявленным первым. Следствие, которое надо принять: если поднять порог в конфиге, скин у игрока
«закроется» обратно. Это устраивает — конфиг локальный, и ровно на этом свойстве держится тестовый
приём «занизить пороги + `cse_profile_reload`».

**`equipped` хранится только в профиле** — это единственный источник правды по надетому скину.
Отсюда следует, что cvar `cse_skins` объявляется **без** `FCVAR_ARCHIVE`: с ним выбор дублировался бы
в `config.cfg`, который общий на машину, тогда как профиль привязан к SteamID64 — второй аккаунт на
той же машине унаследовал бы чужой скин. Направление одностороннее: `CSE_LoadProfile()` (и любая
команда `cse_skin`) выставляет cvar через `Cvar_Set`, обратно cvar в профиль не читается.
На загрузке `equipped` валидируется по текущему уровню: надет недоступный скин → молча откат на
стоковую модель.

Установка конфига — `tools/install_progression.ps1` по образцу `tools/install_hud_layout.ps1`
(идемпотентное копирование), вызов добавить в `build-cse.cmd`.

Сохранение — не на каждое событие: по концу раунда, на фронте `m_iIntermission` и на выходе
(`CHud::Shutdown`, `cl_dll/hud.cpp:594`, зовётся из `HUD_Shutdown`, `cl_dll/cdll_int.cpp:126`),
чтобы не писать файл в бою.

3. **Регресс на дельту счёта** (главное, ради чего правило `delta == +1`): сыграть 3 раунда, выйти,
   зайти обратно в тот же матч → `cse_stats` **не** прибавил ни одной победы/поражения за факт входа.
4. **Регресс на сброс:** `sv_restart 1` в консоли сервера (cvar есть в ReGameDLL,
   `regamedll/dlls/game.cpp:35`) → счёт обнуляется, `cse_stats` не меняется, следующий выигранный
   раунд снова даёт `round_win`.
5. Зайти спектатором, дождаться конца раунда → XP не начисляется.
6. **Регресс на матч:** зайти под конец матча, не сыграв ни раунда, дождаться конца карты →
   `match_wins`/`match_losses` не изменились.

**Коммит.**

## Этап 2 — флаг «бот» с сервера (нужен форк из этапа 1.5)

Определить бота на клиенте нечем: в `hud_player_info_t` флага нет, и движок не ставит фейк-клиентам
userinfo-ключ `*bot` (проверено — grep по `src/xash3d-fwgs/engine/` пуст). Значит источник только
серверный, `FL_FAKECLIENT`.

Боты вытесняемые, слот может сменить владельца, поэтому флаг читается **в момент килла**, а не
кешируется при подключении.

- Сервер: регистрация сообщения `CseInfo` рядом с прочими `REG_USER_MSG` (`regamedll/dlls/client.cpp:169`
  — там же, где `gmsgTeamScore`); широковещательная отправка битовой маски слотов-ботов при
  подключении/отключении клиента и на старте раунда. Маска — 4 байта (`WRITE_LONG`), бит `i` =
  слот `i`; при `maxplayers > 32` слоты сверх 32 считаются людьми (в CS 1.6 предел и так 32).
- Клиент: `HOOK_MESSAGE_FUNC("CseInfo", ...)`, маска кладётся в `cse_profile.cpp`; `CSE_AwardXP()`
  для килла умножает на `bot_multiplier`, если бит жертвы взведён.

Пересылка на коннект закрывает вытеснение бота живым игроком: человек занял слот → пришёл коннект →
маска переслана, бит снят.

На чужих серверах сообщение не придёт — маска нулевая, все считаются людьми (осознанная деградация).

**Проверка:** килл бота даёт 30 XP, килл живого игрока со второго клиента — 100 XP; после вытеснения
бота живым игроком тот же слот сразу даёт полный опыт. **Коммит.**

## Этап 3 — генератор перекрасов

`.mdl` GoldSrc хранит текстуры 8-битными индексами с 256-цветной палитрой:
`mstudiotexture_t { char name[64]; int flags; int width, height, index; }`, по `index` лежат
`width*height` байт индексов и следом 768 байт RGB-палитры. **Перекрас = преобразование только
палитры**, геометрия и анимации не трогаются — самый дешёвый и безопасный способ.

- `tools/mdl_recolor.py` — Python (интерпретатор уже обязателен, `src/cs16-client/CMakeLists.txt:10`).
  Вход: исходный `.mdl`, сдвиг тона/тонировка, выход. Обрабатывает случай `numtextures == 0`, когда
  текстуры лежат в отдельном `<name>T.mdl`.
- `src/cse/cstrike/scripts/CseSkinRecipes.txt` — рецепты: исходная модель, преобразование, имя выхода.
- `tools/install_skins.ps1` — запускает генератор, кладёт результат в `runtime/cstrike/models/cse/`.

⚠️ Сгенерированные модели — производные от лицензионных ассетов Valve, поэтому **в git не
коммитятся** (та же причина, по которой `runtime/` в `.gitignore`). В репозиторий едут только скрипт
и рецепты; модели создаются на машине владельца лицензии.

**Проверка:** после `install_skins.ps1` в `runtime/cstrike/models/cse/` лежат 8 файлов (v_ и p_ для
4 комбинаций), открываются просмотрщиком моделей и отличаются цветом. **Коммит.**

## Этап 4a — скины: свой вид (клиент, форк не нужен)

- `cse_skins.cpp` — таблица из `CseProgression.txt`, состояние «надето», команды
  `cse_skin <weapon> <skin>` и `cse_skin_list`. Разблокировка **вычисляется** по текущему уровню
  (отдельного списка `unlocked` нет, см. этап 1); надеть неразблокированный скин нельзя.
- `cl_dll/cs_wpn/cs_weapons.cpp:434` — `szViewModel` пропускается через подменялку перед
  `gEngfuncs.CL_LoadModel()`.
- Публикация выбора: cvar `cse_skins` с `FCVAR_USERINFO` — **без** `FCVAR_ARCHIVE` (хранилище —
  профиль, см. этап 1). Значение — компактное `ak47:gold;awp:red`.

⚠️ **Значение выставлять через `gEngfuncs.Cvar_Set("cse_skins", ...)`** (образец —
`cl_dll/ammo.cpp:886`), а **не** через `pfnClientCmd("setinfo ...")`, как это делает TeamBar
(`cl_dll/hud/teambar.cpp:277`). У TeamBar значение — голое число, а у нас в нём `;`, который
консольный парсер движка трактует как разделитель команд и обрежет строку. `Cvar_Set` идёт мимо
парсера команд.

Ограничения на значение (`Info_SetValueForStarKey`, `src/xash3d-fwgs/engine/common/infostring.c:410-431`):
запрещены `\`, `"` и подстрока `..`; длина значения ≤ `MAX_KV_SIZE - 1` = **127** символов (не 255 —
`MAX_INFO_STRING` это размер всей userinfo-строки целиком). Наш формат `ak47:gold;awp:red` — 17
символов, запас есть, но при росте числа стволов лимит станет реальным.

**Проверка этапа 4a:** `cse_skin ak47 gold` → скин виден себе от первого лица; `cse_skin_list`
показывает недоступные скины как заблокированные; скин выше уровня не надевается; удалить файл
модели → игра не падает, оружие стоковое. **Коммит.**

## Этап 4b — скины: вид для всех (сервер, нужен форк из этапа 1.5)
- `regamedll/dlls/client.cpp`, `ClientUserInfoChanged` — `GET_KEY_VALUE(infobuffer, "cse_skins")`,
  разбор в состояние игрока.
- `regamedll/dlls/weapons.cpp`, `CBasePlayerWeapon::DefaultDeploy` — подмена `szWeaponModel` перед
  `ALLOC_STRING`. Это же покрывает случай выключенного предсказания: функция присваивает и
  `viewmodel`, и `weaponmodel`.
- **Precache.** В GoldSrc отсутствие precache для `pev->weaponmodel` фатально. Стоковые `p_`-модели
  precache'ятся не в файле оружия — найти место (`grep -rn "p_ak47" regamedll/`) и добавить туда же
  все модели скинов; если места нет — precache в `Precache()` каждого затронутого оружия. Лимит
  движка на модели (512) не под угрозой: +8 файлов.
- Защита: файла скина нет → откат на стоковую модель, без краша.
- Доверие: сервер берёт выбор скина из userinfo как есть и **не проверяет уровень** — уровень живёт
  только на клиенте. Это осознанно: прогрессия личная, не рейтинговая (см. риски).

**Проверка этапа 4b:** два клиента на одном сервере. У игрока с надетым скином на **втором** клиенте
оружие в руках первого — того же цвета. Смена скина на лету (`cse_skin ak47 red`) доезжает до второго
клиента после следующего deploy. Удалить файл модели на сервере → сервер не падает, у всех стоковая.
**Коммит.**

## Риски

| Риск | Смягчение |
|------|-----------|
| ReGameDLL — чужой репозиторий | Этап 1.5: свой форк + перевод submodule (как `mainui_cpp`). Не блокирует этапы 1, 3, 4a, 5 |
| `TeamScore` — трансляция счёта, а не событие раунда | Правило `delta == +1` + засев первого сообщения за карту (этап 1). Регресс-тесты 3–6 в проверке этапа 1 |
| Матчевый XP за матч, в котором не играл | Начисление только при `m_iRoundsThisMap > 0` (этап 1) |
| Надетый скин раздваивается между профилем и `config.cfg` | Единственное хранилище — профиль; cvar `cse_skins` объявлен **без** `FCVAR_ARCHIVE`, поток данных односторонний профиль → cvar |
| Точка precache стоковых `p_` моделей не найдена заранее | Поиск на этапе реализации; фолбэк — precache в `Precache()` каждого оружия |
| Локальный файл профиля правится блокнотом | Принято: прогрессия личная, не рейтинговая. Сервер уровень не проверяет. Античит вне задачи |
| Запись профиля через `fopen` в gamedir может не пройти (read-only каталог, запуск с `-rodir`) | Проверять код возврата `fopen`, при отказе — один `Con_Printf` и работа в памяти без падения |
| Чужой сервер | Опыт копится, скины видит только владелец, боты считаются людьми |
| `;` в значении userinfo обрезается консольным парсером | Ставить cvar через `gEngfuncs.Cvar_Set`, а не `setinfo` через `pfnClientCmd` (этап 4a) |
| Off-by-one в `TeamScore` | Хирургический фикс в этапе 1. Пишет в пустой слот, не за границу — гигиена табло, прогрессия от `g_TeamInfo` не зависит |
| Лицензионные модели отсутствуют в репозитории | Генератор работает на машине владельца лицензии, результат в gitignored `runtime/` |

## Что осталось непроверенным

Честный список того, что не подтверждено чтением кода и выяснится на реализации:

- **Где precache'атся стоковые `p_`-модели** в ReGameDLL. Фолбэк описан, но место не найдено.
- **Приоритет предсказания над серверным `pev->viewmodel`** при включённом `cl_lw`: клиентская
  подменялка (4a) и серверная (4b) пишут в одно поле. Ожидание — при включённом предсказании
  выигрывает клиент, при выключенном сервер, и обе кладут одну и ту же модель, так что расхождения
  не видно. Проверить на этапе 4b двумя клиентами.
- **Формат внутренностей `.mdl`** для перекраса — структура описана по спецификации GoldSrc, но на
  конкретных файлах CS 1.6 не проверялась (в репозитории их нет).
- **Поведение `m_iIntermission` в CS**: считаем, что при завершении карты сервер шлёт `Intermission`
  и поле встаёт в 1. Если окажется, что CS этого не делает, `match_win`/`match_loss` придётся вешать
  на другой сигнал — но статистика раундов от этого не страдает.
