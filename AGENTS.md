# counter-strike-extended

Мета-репозиторий поверх движка Xash3D FWGS (`src/xash3d-fwgs`, submodule) и клиента CS16Client (`src/cs16-client`,
submodule) — Half-Life-совместимый движок + реверс-инженеренный клиент Counter-Strike 1.6. Собственный код
репозитория — обвязка: `.gitmodules`, `.gitignore` рантайма, вспомогательные скрипты в `tools/`.

## Правило собственного кода — `src/cse/`

**Все моды, переводы, ассеты, конфиги и любой кастомный код проекта —
хранить ТОЛЬКО в `src/cse/`.** Не в submodule (`src/xash3d-fwgs`,
`src/cs16-client`), не прямо в `runtime/` (gitignored), не в корень репозитория.
Развёртывание в `runtime/` — через идемпотентные install-скрипты в `tools/`
(см. `tools/install_localization.ps1` для локализации).

## Правила обновления Obsidian

При изменении функциональности файла/метода — найди заметку компонента в vault и обнови на месте. Устаревший
метод помечай `~~methodName~~ (удалён: [дата])`, новый — добавляй в таблицу методов. Новый файл/компонент →
создай/дополни заметку в `{Domain}/`, добавь ссылку в `Index.md`; для крупных компонентов — ещё `-ProjectMap.md`.
Изменилась архитектура в целом → обнови `Архитектура.md`. Changelog не ведём — история в git.

Submodule `src/xash3d-fwgs` и `src/cs16-client` — сторонний апстрим-код (FWGS / Velaron). Заметки о них описывают
роль в сборке и точки интеграции, не внутреннюю структуру апстрима — при обновлении версии submodule сверяй,
не изменился ли способ сборки/установки.

## Правила чтения файлов проекта

Для широкого исследования кода (структура, домены, где что лежит) — используй суб-агента `Explore` с
`model: "haiku"`. Для точечной правки конкретного файла и для заметок Obsidian — читай напрямую через `Read`.

## Быстрые команды

- Сборка движка: Waf, внутри `src/xash3d-fwgs` (см. `src/xash3d-fwgs/README.md`)
- Сборка клиента: `cmake --preset <preset>` внутри `src/cs16-client`, затем `cmake --build build` и
  `cmake --install build --prefix <путь-к-установленному-движку>` (см. `src/cs16-client/README.md`)
- Инициализация submodules: `git submodule update --init --recursive`

## MCP-сервер `game` (tools/mcp-game)

Локальный MCP-сервер на TypeScript (`@modelcontextprotocol/sdk`), зарегистрирован в `opencode.json` под ключом
`mcp.game`. Запускается через `npm start --prefix tools/mcp-game` (tsx выполняет TypeScript напрямую). Один сервер
с несколькими tools — реализует типовые шаги dev-цикла без ручного вызова shell-команд:

| Tool              | Что делает                                                                                                       |
|-------------------|------------------------------------------------------------------------------------------------------------------|
| `build_engine`    | `waf build` (+ опционально `clean`/`rebuild`) в `src/xash3d-fwgs`, затем `waf install --destdir=build/engine`. Configure НЕ запускает (одноразовая ручная операция с `--sdl2`). |
| `build_client`    | `cmake --build build --config <cfg>` + `cmake --install build --prefix=build/cs16-client` в `src/cs16-client`. По умолчанию пресет `win32-release-x86`; configure пропускается, если `build/CMakeCache.txt` уже есть. |
| `deploy_runtime`  | Копирует артефакты из `build/engine` → `runtime/` и из `build/cs16-client/cstrike` → `runtime/cstrike/`. Поддерживает `target` (engine/client/all), `include_pdb`, `dry_run`. |
| `run_game`        | Запускает `runtime/xash3d.exe` (detached, non-blocking), возвращает pid. Параметры: `game`, `map`, `windowed`, `width/height`, `dev`, `extra_args`, `log_file`. |
| `stop_game`       | Останавливает xash3d по pid или все экземпляры сразу (`taskkill /F`).                                            |
| `game_status`     | Показывает, запущен ли xash3d, и его pid(ы).                                                                     |
| `tail_log`        | Хвост `runtime/engine.log` (или другого файла в runtime/) прямо в чат.                                          |
| `project_paths`   | Диагностика: печатает все пути, которые сервер резолвит из корня репозитория.                                    |

ВАЖНО: MCP-сервер общается по stdio, поэтому весь stdout дочерних процессов (waf/cmake/xash3d) перехватывается
сервером и не выводится наружу — для лога используй `tail_log` или смотри `runtime/engine.log`. Любые
диагностические сообщения сервер пишет в stderr.

## Правила работы с Git репозиторием

- Запрещено создавать ветки для работы со своей задачей, всегда работать с текущей веткой, если явно не сказано работать в отдельной

- Если большая задача с планом то после каждого этапа делать комит со своими изменениями, пуш не делать если явно не сказано

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.
